## 1. Phase 1 調査結果

### 既存リポジトリ

- 開発環境：Windows 11 / Node.js 24 / npm 11。**macOS・Xcode が無いため iOS ビルドと iOS 実機確認はこの環境ではできない。**

### 技術スタックと選定理由

| 用途 | 採用 | 理由 | 代替案 |
|---|---|---|---|
| UI | React 19 + TypeScript | 指示書の第一候補。型でデータモデルを守れる | Vue / Svelte |
| ビルド | Vite 8 | 高速、PWA プラグインあり | — |
| 端末内DB | Dexie 4（IndexedDB） | ブラウザ・iOS WebView 共通で動く。ライブクエリで画面が自動更新される | localForage、SQLite（Capacitor プラグイン） |
| PDF表示 | pdf.js 6（legacy ビルド） | 唯一の実用的な OSS PDF レンダラ。legacy ビルドで古めの iOS にも対応 | ネイティブ PDFKit（iOS 専用） |
| バックアップ | fflate | 小さく高速な ZIP ライブラリ。ストリーミング書き出しでメモリを抑えられる | JSZip |
| オフライン | vite-plugin-pwa（Workbox） | アプリ本体と pdf.js の CMap/フォントを事前キャッシュ | 手書き Service Worker |
| 画面遷移 | react-router（HashRouter） | Capacitor でサーバー設定なしに動く | — |
| テスト | Vitest + fake-indexeddb、Playwright（Edge） | DB 処理の単体テストと、実ブラウザでの通し確認 | — |

外部 API・広告 SDK・解析 SDK は一切使用していない。外部通信は「購入先URLを開く」操作のみ。

### iOS アプリとしての配信方法
- Capacitor 8 で Web アプリを iOS アプリに包む（`ios/` に Xcode プロジェクトを生成済み。CocoaPods 不要の Swift Package Manager 構成）。
- Mac がないため、GitHub Actions のクラウド Mac でビルドし TestFlight へアップロードする（手順は [IOS_RELEASE.md](IOS_RELEASE.md)）。
- アプリ本体は端末に同梱されるため、iOS アプリでは Service Worker を使わずにオフライン動作する（`main.tsx` でネイティブ時は登録しない）。

### ブラウザ版と iOS 版の差分

| 機能 | ブラウザ（PWA） | iOS アプリ（Capacitor・予定） |
|---|---|---|
| オフライン起動 | Service Worker で対応済み | アプリ同梱で対応 |
| PDF を共有メニューから受け取る | **非対応**（iOS Safari は Web Share Target 非対応） | 実装済み（PDF・画像の書類タイプを登録。受け取り後に新規作品／既存作品への追加を選択）。**実機未確認** |
| PDF をファイルから選択 | 対応済み | 対応（WebView の file input） |
| バックアップの保存 | ダウンロード、またはタッチ端末では共有シート | Filesystem・Share プラグインで共有シートを開く（実装済み・**実機未確認**） |
| データの自動削除リスク | Safari（ホーム画面に追加していない場合）は**7日間アクセスがないとデータが削除されうる** | WebView の IndexedDB は容量逼迫時に削除されうる（下記リスク参照） |
| 画面の消灯防止 | Wake Lock API（Safari 16.4+） | 同左（必要ならプラグイン） |

## 2. データ設計

- `patterns`：作品。お気に入りはステータスと独立したフラグ。カテゴリは別テーブルで自由に追加可能。
- `files`：作品に属するファイルのメタデータ（種別・ページ数・閲覧位置）。**PDF の実体は持たない。**
- `blobs`：ファイル実体。1ファイル=1実体で共有しないため、削除しても他の作品に影響しない。
- `counters`：段数カウンター（作品単位）。
- `annotations`：書き込み（ファイル単位・ページ単位）。座標はページの幅・高さに対する 0〜1 の割合なので、倍率や画面サイズが変わってもずれない。元の PDF は変更しない。

削除時の扱い：
- 作品を削除 → その作品のファイル実体・カウンター・書き込み・表紙も削除（確認ダイアログで件数を表示）。
- ファイルを削除 → そのファイルの実体と書き込みのみ削除。
- カテゴリを削除 → 作品からカテゴリの割り当てだけ外す（作品は残る）。

## 4. リスクと対策

1. **端末内データの消失**：ブラウザ・WebView のストレージは OS やブラウザにより削除されうる。
   対策：`navigator.storage.persist()` の要求、設定画面でのバックアップ導線と最終バックアップ日時の表示。
   iOS アプリ化の際は、ファイル実体を Capacitor Filesystem（アプリの Documents 領域）へ、メタデータを SQLite へ移すことを推奨（`repo.ts` に保存処理を集約してあるため置き換えやすい構成）。
2. **大きな PDF・大量データでのメモリ**：表示は前後1画面分のページだけ描画し、それ以外は解放。canvas は iOS の上限より小さく抑えている。バックアップは ZIP をストリーミングで生成するが、復元時は ZIP 全体をメモリに読み込むため、数百 MB を超えるバックアップは実機での検証が必要。
3. **日本語 PDF の表示**：埋め込みフォントのない日本語 PDF のために CMap と標準フォントをアプリに同梱（オフラインでも表示可能）。
4. **App Store 審査**：Web をそのまま包んだだけのアプリは審査で指摘されることがある（ガイドライン 4.2）。オフライン動作・ファイル管理・カウンターなどアプリとしての機能は備えているが、共有メニュー対応などネイティブ連携があると有利。

## 5. 開発・テスト方法

```bash
npm install
npm run dev        # 開発サーバー
npm test           # 単体テスト（Vitest）
npm run build      # 型チェック + 本番ビルド
npm run test:e2e   # ブラウザでの通し確認（build 後。Windows は Edge、他は BROWSER_PATH を指定）
```
